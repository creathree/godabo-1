# ルールブック（Git・環境変数・デプロイ）

[creathree](https://github.com/creathree) 上で **ソース公開** する前提の運用ルールです。  
「うっかり秘密を push しない」「環境ごとに設定を分ける」ための共通の型をここにまとめます。

---

## 1. 大原則（3つだけ覚える）

1. **秘密はリポに入れない。** 値はホスティングの Secret 機能か、手元の `.env.local` だけ。
2. **リポに入れるのは「名前」と「雛形」だけ。** 例: `.env.example`、入力待ちの `cloudflared/godabo-1.yml`。
3. **デプロイは「ビルド成果物 + 実行環境の変数」。** ローカル専用のパスや個人の Tunnel credentials は本番に持ち込まない。

迷ったら、そのファイルを GitHub に公開して困るかで判断してください。

---

## 2. Git に載せるもの・載せないもの

### 載せる（公開してよい）

| 種類 | 例 |
| --- | --- |
| アプリのソース | `app/`、`components/`、`lib/` |
| 共有設定の雛形 | `.env.example`、`cloudflared/godabo-1.yml`（`<INPUT_…>` のまま） |
| ドキュメント | `docs/`、`README.md`、`AGENTS.md` |
| 依存の宣言 | `package.json`、`package-lock.json` |
| ツール設定 | `i18n-config.js`（**apiKey は env 参照のみ**） |
| エディタ設定（方針次第） | `.vscode/` — チームで Run on Save を共有する場合 |

### 載せない（`.gitignore` で除外）

| 種類 | なぜ |
| --- | --- |
| `.env.local` など実値入り env | API キー・個人設定が含まれる |
| `node_modules`、`.next/` | 再生成できる・巨大 |
| `~/.cloudflared/` 相当の credentials | トンネル乗っ取りに直結 |
| 埋め済みの Tunnel config | ホスト名・トンネル ID とセットで機微 |
| `package.local.json` | 個人用 script 上書き用（任意） |
| `.bracket-i18n-paused` | ローカルの作業状態 |

### 特別: `.env.example`

- **コミットする。** 変数名とコメントだけ。値は空か、ダミーのプレースホルダ。
- 新しい環境変数をコードに足したら、**同じ PR で `.env.example` も更新**するのがルールです。

---

## 3. `.env` ファイルの扱い

### このリポでの役割分担

| ファイル | 用途 | Git |
| --- | --- | --- |
| `.env.example` | 「こういう変数がある」一覧 | **載せる** |
| `.env.local` | 手元開発用の実値（Gemini、Tunnel パスなど） | **載せない** |
| `.env.development` | 使う場合のみ。チーム共有の非秘密デフォルト | 原則載せない |
| `.env.production` | 本番値はホスティング側に置くのが基本 | **載せない** |

ルートの `.gitignore` は `.env*` を除外し、**`!.env.example` だけ許可**しています。

### 初めてクローンした人向け

```bash
cp .env.example .env.local
# 必要になったらだけ値を入れる（第二回土台では空でも可）
```

- `npm run dev` / `npm run build` — 多くの場合、キーなしで動く。
- `npm run i18n:fill` — `GEMINI_API_KEY` が必要（後から一括でも可）。
- `npm run dev:tunnel:named` — `CLOUDFLARED_*` が必要（永続トンネル用）。

### コード側の約束

- `i18n-config.js` の `apiKey` は **`process.env.GEMINI_API_KEY` のみ**。ファイルにキーを書かない。
- `package.json` に **個人の絶対パスを書かない**（Tunnel は env または即席 `dev:tunnel`）。

### bracket-i18n と env の読み込み

`fill` は Next.js に近い順で dotenv を読みます（開発時は `.env.development.local` → `.env.local` → …）。  
詳細は [bracket-i18n の README](https://www.npmjs.com/package/bracket-i18n) を参照してください。

## 4. `.gitignore` の見方（このリポ）

意味のあるブロックだけ抜粋します。全文はルートの `.gitignore` が正本です。

| ブロック | 意図 |
| --- | --- |
| `node_modules` / `.next` | ビルド・インストールの再現物 |
| `.env*` + `!.env.example` | 秘密の一線 |
| `*.pem`、`**/credentials*.json`、`.cloudflared/` | TLS・Tunnel の資格情報 |
| `package.local.json` | 個人用 npm 上書き |
| `.bracket-i18n-paused` | 多言語 scan 一時停止フラグ |

`.gitignore` に載っていても、**すでに Git 履歴に入った秘密は消えません。** 一度 push したキーはローテーション（再発行）を検討してください。

## 5. コミット前チェックリスト

公開リポ向けに、push 前に短く確認する項目です。

- [ ] `git diff` に `.env`、`.pem`、`credentials`、埋め済み yml が **含まれていない**
- [ ] 新規の環境変数があるなら `.env.example` に名前を足した
- [ ] コメントに個人名・社内だけの URL・本番キーがない
- [ ] `npm run build` が通る（可能なら）
- [ ] コミットメッセージは変更の意図が読める（creathree の他リポに寄せる）

### bracket-i18n を触っていない段階

- `npm run i18n:pause` 中なら、そのままコミットして問題ありません（`.bracket-i18n-paused` は無視されます）。
- 途中の `[[…]]` を意図せず scan させたくないときも pause が有効です。

## 6. デプロイの基本ルール（現時点）

本番のホスティング先はこれから決めてもよいですが、**どこでも共通** の型だけ先に固定します。

### ビルド

```bash
npm ci
npm run build
npm run start
```

- CI では `npm ci` を使い、`package-lock.json` と揃える。
- ビルド時に必要な **公開** 変数だけ `NEXT_PUBLIC_*` 等で渡す。秘密は `NEXT_PUBLIC_` にしない。

### 秘密の置き場所

| 環境 | 置き場所 |
| --- | --- |
| ローカル | `.env.local` |
| CI（必要な場合） | GitHub Actions の Secrets（Organization / Repository） |
| 本番ランタイム | 利用する PaaS・Cloudflare・自前サーバの Secret 管理 |

**Git のタグや Release に env ファイルを添付しない。**

### Tunnel と本番

- 開発: [cloudflareトンネルの作り方](./cloudflareトンネルの作り方.md)。
- 本番: Tunnel でも直接デプロイでもよいが、**credentials はデプロイ先の Secret にのみ**。

### デプロイ前の最小確認

- [ ] 本番用の環境変数がホスティング側に登録済み
- [ ] `NODE_ENV=production` で起動している
- [ ] ログに API キーや Authorization ヘッダが出ない

---

## 7. もし秘密を push してしまったら

1. **そのキーを無効化・再発行する**（Git から消すだけでは足りない）。
2. 履歴からの完全除去は `git filter-repo` 等が必要になる場合がある。creathree の管理者と相談。
3. 原因をこのルールブックに沿って防ぐ（`.env.example` のみ、pre-commit 等は組織方針に従う）。

## 8. Git の連載運用（note と履歴）

| 項目 | ルール |
| --- | --- |
| 既定ブランチ | `main`（creathree の公開リポに合わせる） |
| 回の目印 | アノテーションタグ `note-第一回`・`note-第二回` …（その回の公開スナップショット） |
| 区切り | 原則 **1 回 = 1 まとまったコミット（＋タグ）**。読者・レビュー担当が `git checkout note-第二回` で再現できるようにする |
| 初回 push | `git remote add origin …` のあと `git push -u origin main --tags` |

組織の方が **ふっと目を通す** 想定でも、上記タグと [説明書](../README.md) が入口です。機能の到達度は回ごとの README に書き、未実装はスコープ外として明示します。
