## 活動主旨（なぜ公開するか）

1. **参加型の 5W1H あそび** — だれが・いつ・どこで・なにを・なぜ・どのようにをみんなで埋め、作品としてともに見る体験の Web フロントを作る（趣旨の要約は [第一回](./第一回/README.md)）。
2. **note 連載に沿った公開開発** — [構想まとめ（note）](https://note.com/nana_nezumi/n/nf4c8147368ae) と同期しながら、コードと日本語の説明書を同じリポジトリで積み上げる。
3. **学習と再現可能性** — 企業・個人を問わず、タグ付きの履歴（`note-第一回` / `note-第二回` …）と docs で「その時点の土台」を追えるようにする。
4. **エコな構成** — Cloudflare の無料枠や Tunnel、Firebase 等を前提に、小規模でも運用可能な形を選ぶ（第一回・第二回の方針）。

これはデモ用の一過性リポジトリではなく、**製品に近い誠実さで育てる学習リポジトリ** です。

## 公開開発で共有したいこと（ゼロトラスト・個人情報）

ゴダボーワンだけを作るのが目的ではありません。参加型サービスでは **個人情報や認証まわりをどう切り分けるか** が設計の中心に来るため、ゼロトラストの考え方に沿った取り組みを、**進行中の例として** このリポジトリと docs に残し、より多くの方と情報を交換したい、という趣旨があります。

ここで書くのは「正解のカリキュラム」ではありません。**creathree がいま検討・実装している例** を公開し、フィードバックや別案を歓迎するためのメモです。上から教える立場は取りません。

### 個人情報の扱い（ゼロトラストの前提）

- **信頼の境界をアプリの内側だけに置かない** — 参加 Room・ログイン後のデータは、将来 Firebase 等を使うとしても、ブラウザとエッジ（Cloudflare）・サーバの境界ごとに「何をどこまで信じるか」を分ける想定です（[第一回](./第一回/README.md) の Middleware + Cloudflare の方針）。
- **収集するなら理由を先に言語化する** — プライバシーポリシー・利用規約は認証機能と **セットで** 用意する予定であり、先に画面だけを広げない方針です（実装前の docs で合意を取り、連載と同じタイミングで更新します）。
- **最小限・局所化** — Room 単位で状態を束ね、永続化の範囲を必要最小に寄せる、という note 第一回のエコ設計を引き続き基準にします。

### 情報漏洩対策（いまリポで見せている例）

| 例 | このリポでの置き方 |
| --- | --- |
| 秘密を Git に載せない | `.env.example` と雛形のみコミット（[ルールブック](./第二回/ルールブック.md)） |
| Tunnel 資格情報の分離 | `cloudflared` の credentials はリポ外、`credentials*.json` を ignore |
| 開発の「窓」を必要時だけ | Cloudflare Tunnel で常時公開ステージングを必須にしない（[Cloudflare について](./第二回/Cloudflareについて.md)） |
| 水際の一次防御 | ルート `middleware.ts` の基本ヘッダー、locale の検証（`LocaleValidate`） |
| ログに秘密を出さない | デプロイ前チェックとしてルールブックに明記（今後の CI 化は検討余地） |

漏洩が起きた場合の手順（キー無効化・履歴の扱い）もルールブックに書いてあり、**同じ型を他プロジェクトに持ち込めるか** の議論に使えるよう残しています。

### 認証・ポリシー制定（これから docs / コードに載せていく例）

note 第一回で示した方向を、実装と並行して **「なぜそうしたか」付きの例** として公開していく予定です（未到達のものは第二回以降のスコープ）。

| テーマ | 方向性の例（検討・実装のたたき台） |
| --- | --- |
| 認証 UI | リダイレクト方式を採用し、ポップアップ認証は避ける |
| 多言語と法的文言 | ロケール別 URL（`ja` / `ko`）と bracket-i18n で UI 文言を管理し、ポリシー文も同じ仕組みで追従させる |
| エッジとアプリの役割 | Cloudflare で水際を固め、アプリ側 Middleware と役割分担する |
| ポリシー文書 | 認証を入れる回と同時期にプライバシー・セキュリティ関連を docs に追加し、バージョンと Git タグで対応付ける |

できあがった版は「こうあるべき」ではなく **「こう組んだ・こう直した」** という記録にします。企業の方が社内ポリシーと比較する材料、個人の方が自分のプロジェクトのたたき台にする材料になれば十分です。

### 共有のしかた

- **コードと docs を同じリポに置く** — 設定の意図が README・ルールブック・回ごとの説明書から辿れるようにする。
- **Issue / PR で差分と意見をもらう** — ゼロトラストや個人情報の整理は分野横断のため、教壇ではなく対話で更新したい。
- **note は背景、リポは正本** — 長い考察は note に書き、再現可能な部分は常に Git 側に寄せる。
